# 架构与设计取舍

## 为什么从确定性数据流程开始

业务报告中的数值必须能够脱离模型独立计算。SQLite 承担本地事实存储，SQL 视图固定会话粒度，Python 处理质量检查、分解与统计。模型仅选择允许的工具并解释证据；任意生成 SQL 不进入执行路径。

MongoDB 是独立文档分析与性能验证路径，同一事件输出成 JSONL，聚合结果按 logical_id 去重，并与 SQLite 在相同截止点对账。示例索引以等值过滤字段开头，再放接收时间范围和逻辑键；具体收益以执行计划和本机测量为准。

## 溯源

- 固定数据种子、生成账本与文件 SHA-256。
- 工作流开始前检查快照完整性。
- 保存工具路由、完整证据、声明核验、提示词哈希、关键源文件哈希与模型标识。
- 本地运行时间及 token usage 单独记录；使用的 API 凭证不落盘。
- 评测保存冻结案例哈希，每条结果对应案例、版本和集合。

## 已知取舍

- SQLite 为可复现展示选择；没有声称其吞吐或运维代表生产数仓。
- 事件时间字段在固定 ISO 格式下按字典顺序比较。生产适配需要严格时间解析、时区与水位线。
- 当前模型路由只提供 analysis、experiment 和 clarify 三种工具，统计实验工具返回固定的模拟案例。
- 提示词要求澄清，但没有把所有指标定义校验编码成强约束；真实调用应通过挑战集评估。
- 声明核验只检查列出的数值和路径，不足以验证摘要、遗漏或结论。通过数值检查仍要求人工复核。
- 模型接口只做单次请求，不自动重试，避免无上限调用；网络/JSON 错误由调用者处理，后续加入有界重试和持久运行状态。
- 本地 demo 不依赖模型，支持低成本复现；规则回归与真实模型评测严格分开表述。
- 当前没有基于人工真值建立自动发布门槛，因此不会把工作流数值检查通过直接等同于可自动发布业务结论。
